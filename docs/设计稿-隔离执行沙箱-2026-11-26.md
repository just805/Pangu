# 设计稿：隔离执行沙箱（M-16）

> 状态：设计稿，未实现。本文档只回答「值不值得做、做成什么样、关键约束是什么」。
> 结论先说：**首期只做「PoC 预验证沙箱」，不做「全工具沙箱」**（§2 说明原因）。

## 1. 为什么做（以及为什么先只做一半）

两条不同的诉求经常被混为一谈：

| 诉求 | 真实价值 | 实现代价 |
|---|---|---|
| A. **执行隔离**：所有工具跑在容器里，不污染部署主机 | 中等（主机污染已有 hostd + 最小权限缓解） | 极高：要改造全部 94 件宿主工具的执行路径 |
| B. **PoC 预验证**：PoC 先在一个仿制环境里跑通，再打真目标 | 高 | 中：只需一个「按指纹起仿制环境 + 执行 PoC」的闭环 |

**B 才是真正的缺口**。现状是：worker 写完 PoC 直接打生产目标，失败就换 payload，
拿不到「这个 PoC 到底对不对」的独立判断——而这正是误报与无效利用的主要来源。
A 的收益远小于代价（且与「不抄重型容器编排栈」的既有决策冲突）。

因此：**首期只做 B**。A 留作长期方向，并且只在「出现真实的主机污染事故」时才重新评估。

## 2. 边界

- **单机 Docker，不是编排**。不引 Kubernetes、不引 Nomad、不做多机调度。
- **不做通用靶场平台**。仿制环境只服务「验证一个 PoC」，不追求可复用的漏洞环境库。
- **不绕过流量录制**。容器出站必须走平台出口（MITM 或代理），否则证据链断在沙箱里。
- **不执行不可信样本**（与 `reverse/` 的「静态分析、不执行样本」同一纪律）。

## 3. 核心流程（PoC 预验证）

```
worker 写 PoC
    │
    ├─(1) poc_prevalidate 工具
    │      ├─ 输入：目标指纹（tech/version/server）+ PoC 命令 + 期望特征
    │      ├─ 环境解析：指纹 → 镜像（如 nginx:1.25 / php:8.1-apache）
    │      ├─ 起容器（含仿制应用的最小子集）
    │      └─ 在容器内执行 PoC，捕获输出
    │
    ├─(2) 判定
    │      ├─ 期望特征命中 → 标记「PoC 可复现」→ 再打真目标
    │      └─ 未命中 → 回给模型「PoC 在仿制环境里没触发」，附完整输出
    │
    └─(3) 证据
           ├─ 容器内请求/响应落流量录制（出口走平台代理）
           └─ 容器日志作为 evidence 附件（save_evidence）
```

## 4. 组件与接口

### 4.1 沙箱运行时

```go
// sandbox 包：单机容器生命周期 + 执行。
type Runtime interface {
    // Start 按镜像与端口映射启动容器，返回容器 ID。
    Start(ctx context.Context, spec Spec) (id string, err error)
    // Exec 在容器内执行命令，返回合并输出与退出码。
    Exec(ctx context.Context, id string, cmd []string) (out string, code int, err error)
    // Stop 停止并回收容器。
    Stop(ctx context.Context, id string) error
}
```

实现只依赖 `docker` CLI（与 `install.sh` 的 Docker 形态同一取向），不引
`docker/docker` SDK——避免为一个功能引入庞大的依赖树。

### 4.2 指纹 → 镜像映射

```go
// 内置映射表（代码常量，可被设置覆盖）：
//   nginx/1.2x      → nginx:<minor>
//   apache/2.4.x    → httpd:<minor>
//   php/8.x         → php:<minor>-apache
//   redis/6.x|7.x   → redis:<minor>-alpine
//   未知             → 直接报错，不猜
```

关键约束：**映射不到就明确失败**，不允许「随便起个 ubuntu 跑一下」——那样验证
没有意义，还会给出错误的「PoC 不可复现」结论。

### 4.3 网络

- 容器网络用 `--network` 自定义 bridge，**出口强制指向平台代理**；
- 若流量录制开启，容器内请求必须经过 MITM（`HTTP_PROXY`/`HTTPS_PROXY` 注入）；
- 目标地址限定为容器内（`127.0.0.1:<mapped_port>`），**禁止访问外部网络**（除代理）：
  `--network` 只连代理所在的网络，或直接用 `--internal` + 代理转发。

> 待确认：现有录制的 MITM 是否支持「容器 → 代理 → 目标（容器内）」的拓扑？
> 如果 MITM 自身在宿主机，容器访问 `127.0.0.1` 会打到容器自己而非映射端口。
> **这是本设计的第一技术风险**，见 §7。

## 5. 与现有机制的适配

| 现有机制 | 如何复用 |
|---|---|
| `hostd`（特权助手） | 容器启停需要 docker 权限；按现状走 hostd 的 unix socket，不新增特权路径 |
| 流量录制（`traffic/`） | 容器出站走平台出口代理，录制在中转处完成（与 Bash 的 `HTTP_PROXY` 同源） |
| 拦截规则（`intercept/`） | `poc_prevalidate` 本身过 PreToolUse；容器内的命令不再单独过规则（否则规则语境失真），但允许的镜像白名单是关键闸门 |
| 后台作业（`job_*`） | 起容器与执行可能超过单轮时限，复用 `job_start` 而不是新增协程 |
| 证据（`save_evidence`） | 容器日志/PoC 输出作为附件 |

**镜像白名单是安全核心**：只允许内置映射表里的官方镜像，禁止任意 `docker run`。
这条约束同时挡住了「用沙箱当跳板」的风险。

## 6. 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | 只做可行性验证：手工起一个 nginx 容器，验证「容器 → 平台代理 → 录制」拓扑是否成立 | 能拿到一条录制的请求 |
| P1 | `poc_prevalidate` 工具：指纹映射 + 起容器 + 执行 + 判定 | 用已知 PoC（如 nginx 版本泄露）验证命中与未命中两条路径 |
| P2 | 证据闭环：容器日志存档 + 报告引用 | 报告里能引用沙箱验证结论 |
| P3（暂缓） | 全工具沙箱（诉求 A） | 仅在出现真实主机污染事故后评估 |

**P0 必须先做**。如果「容器 → 代理」拓扑走不通，整个设计要推翻重来——这也是为什么
本文档只是设计稿而不是实现。

## 7. 风险与待确认

1. **拓扑（最高风险）**：MITM 跑在宿主机还是容器？容器如何访问到它？端口映射后
   容器内 `127.0.0.1` 指向容器自身，需要用 `host.docker.internal`（Linux 要
   `--add-host=host.docker.internal:host-gateway`）。
2. **镜像体积**：每起一个容器要拉镜像。离线环境需要预拉取（可放进 Dockerfile 的
   工具层，与 nuclei/playwright 同等处理），否则 P1 在无外网环境不可用。
3. **资源限额**：必须设 `--memory` / `--cpus` / `--pids-limit`，否则一个失控的
   PoC（如 fork 炸弹）会打垮宿主。这是硬要求，不是可选项。
4. **合法性**：仿制环境本身是本地容器，不涉及外部目标；但「PoC 打真目标」仍需
   授权范围守卫（已有的 N2 守卫覆盖）。
5. **环境失真的代价**：仿制环境与真目标可能差异很大（中间件配置、补丁级别）。
   验证通过不等于真目标可复现——**报告措辞必须保留这个不确定性**。
