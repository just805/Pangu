# 模块新增需求分析（2026-11-26）

> 基线：v0.1.27 + main 未发版提交。目的：在**不动现有架构**的前提下，回答
> 「平台还缺哪些功能模块、每个模块为什么做、做成什么样、怎么接到现有机制上」。
> 本文只做需求分析，不含实现设计；立项前先看 §7 的未核实项。

## 0. 一页结论

- **平台现状**：一次性、授权范围内的自主渗透测试闭环已经完整——目标拆解 → planner/worker
  闭环 → 三层拦截 → 双图写回 → 证据闸门 → Word 报告。这块不建议再加大模块，只做打磨。
- **主要缺口集中在四个方向**：
  1. **挖得不够深**：只有内容发现型模糊（ffuf），没有协议/API 契约级 fuzz；源码与成分扫描结果进不了图谱；越权测试缺结构化权限模型。
  2. **只能做一次性测试**：没有周期任务、资产快照与变更检测，无法做持续型外部攻击面管理。
  3. **验证结论的可信度还差最后一环**：模型自述的「已排除」没有证据要求，AI 定级没有确定性上下限。
  4. **平台是封闭的**：只有单管理员会话登录，没有开放 API Key，也不能作为 MCP 服务端被外部 Agent 调用。
- **建议新增 16 个模块**，分四个梯队（§4），其中 5 个属于「补核心竞争力」，建议优先。
- **已有明确决策不做的**（§6）：多用户、SRC/众测项目档案、自动复测、向量经验库、分布式执行节点。

## 1. 分析方法与判定口径

**输入材料**

- `CHANGELOG.md` 的 0.1.x 段（0.1.0 → 0.1.27）全部条目标题
- `README.md`、`AGENTS.md`（构建、注册、拦截、迁移的硬约束）
- `db/schema.sql` 全部 62 张表（数据模型事实）
- 路线图与对比文档：`深度优化方案-2026-10-31.md`、`漏洞挖掘能力对比.md`（G1–G5、M1–M25）、
  `同行对比分析-2026-11.md`（P0/P1/P2）、`产品优化清单-2026-10-29.md`
- `hosttools/hosttools.go` 工具清单、`web/src/app` 32 个路由

**缺口判定分三档，正文每个模块都标注**

| 档位 | 含义 | 可信度 |
|---|---|---|
| 【代码核实】 | 直接看了表结构 / 路由 / 工具清单，确认不存在 | 高 |
| 【文档记载】 | 路线图或 CHANGELOG 明确写着「待做 / 顺延 / 未实现」 | 高 |
| 【检索未见】 | 按关键词检索没有命中，但没逐行读代码 | 中，立项前需复核 |

【检索未见】为什么可信度只给中：`漏洞挖掘能力对比.md` 开头自己记着——那次盘点曾两次
因 grep 无输出误判能力缺失。所以本文凡是这一档的，都在 §7 单列，立项前先复核。

**一条已知的取舍**：路线图里「已发版」的旧条目（v0.3.x / v0.4.x）本文一律视为已具备，
不重复列为缺口；只有文档写明「顺延 / 未开始 / 待做」的才进清单。

## 5. 模块详述

### 第一梯队：补核心竞争力

#### M-01 模糊测试引擎

- **定位**：把 vuln-hunting 方法论里「数据边界」「资源假设」两个维度从「模型手写脚本」
  变成「平台可编排的工具」，对标 G1 / M7。
- **核心功能需求**
  - 支持三类入口：OpenAPI / GraphQL 契约驱动的 API 模糊（schemathesis 类）、协议模糊
    （boofuzz 类）、基于已录流量的参数变异。
  - 模糊任务可后台长跑，进度与异常样本回写探索图。
  - 异常样本自动进入现有的证据链：请求响应落流量录制，可一键转 finding。
  - 限速 / 请求总数 / 时长上限可配，并在模糊开始前过拦截规则。
- **与现有平台的适配逻辑**
  - 复用「只落脚本 + 组命令，不自己发请求」的领域工具模式（`agent/tools_probe.go`）：
    流量照常过 MITM 留痕，审批照常生效。
  - 长跑走既有 `job_*` 后台作业，不新增后台协程。
  - 契约来源直接用已有的 `api_contract` 工具产出；变异种子用 `traffic_search`。
  - 宿主工具按三类源加进 `hosttools`，「宿主环境」页自动可装。
  - 新工具必须进 `PlannerTools / WorkerTools / MainAgentTools` 三张清单和
    `agent/toolcatalog.go` 的 BuiltinToolSeeds（历史上 listener 栽过）。

#### M-02 代码资产与 SAST/SCA 联动

- **定位**：让「源码仓库」成为一等资产，把静态扫描和成分分析结果接进双图，在 SAST 与
  动态挖掘之间架桥。对标 G3 / M8 / M23。
- **核心功能需求**
  - 代码资产：登记仓库地址或上传源码包，按授权范围归属到企业。
  - SAST 结果（semgrep / gitleaks）结构化入库：文件、行、规则、代码片段。
  - SCA 结果（trivy）转成组件 → 版本 → CVE，与 `vulnintel` 的 CPE 匹配打通。
  - worker 能按运行时资产（域名 / URL）反查关联的源码位置，拿到 sink 上下文。
  - 「按 diff 增量扫描」作为后续扩展，不在首期。
- **与现有平台的适配逻辑**
  - 资产类型在 `assets` 上新增 kind，不另建资产体系；范围归属沿用 `company_scope`。
  - 写回走 `insert_assets` 的资产拦截闸门与 `record_fact` 的锚点规则；新增一个
    `record_code_findings` 写入工具时必须同样过范围守卫（代码仓库路径也在授权范围内）。
  - 组件 → CVE 复用 `vulnintel/link.go` 的指纹归一匹配；结果作为 hint 节点挂到探索图。
  - 技能 `source-code-hunting` 已存在，补「工具映射」一节即可，不新建技能。
  - 逆向模块（`reverse/`）已有样本上传与分片上传链路，源码包上传复用同一条路。

#### M-03 角色权限矩阵

- **定位**：越权测试的前提是「有两个身份、知道谁能访问什么」。把角色、接口、权限的
  对应关系从「模型从流量里现推」变成任务里的结构化数据。对标 M15。
- **核心功能需求**
  - 从接口清单（`api_contract`）、登录态（`session_login`）、流量录制中半自动抽取
    「角色 × 接口 × 期望访问结果」矩阵。
  - 人工可修正；修正结果随任务沉淀。
  - 按矩阵自动生成越权测试对：同角色换 ID（水平）、低权角色访问高权接口（垂直）。
  - 测试结果直接产出 finding，证据绑定基线与对照两条流量。
- **与现有平台的适配逻辑**
  - 数据放在探索图（新节点 kind 或 fact 的一种 payload 类型），随任务走，不污染全局资产图。
  - 执行零成本复用：`http_request(session=同名)` 的会话复用 + `http_replay` 原样重放基线
    + 只换身份重放对照（N3 设计的本意就是这个场景）。
  - 判定差异用已有 `diff_responses`（保留键增删、抹凭据字段）。
  - 与攻击链联动：越权 finding 通过 `finding_chain_edges` 接入「初始访问 → 最终影响」叙事。

#### M-04 三态收口与确定性定级约束

- **定位**：把「模型自我判定不作数」贯彻到底。两件事：① 结论只能是
  confirmed / ruled_out / open_proof_gap 三态，排除必须指名控制点；② AI 定级受确定性
  规则的上下限约束。对标 M11 / M20 / M21 与 CVEngine 的 floor / ceiling。
- **核心功能需求**
  - 「已排除」必须填写：哪个防护、位于攻击路径的哪一步、由哪次请求证明。
  - 未执行的检查报「未验证」，不得静默通过。
  - 定级下限：确定性证据命中（nuclei / sqlmap 实测）时 AI 不得低于该等级。
  - 定级上限：仅有版本匹配证据时，AI 最高只能给「待验证」。
  - 相同证据签名只裁决一次，省 judge 调用。
- **与现有平台的适配逻辑**
  - 已有的机械证据闸门、逐字回验（`agent/tool_outputs.go`）、确定性复核是下限的雏形，
    本模块是补上限和排除态，不推倒重来。
  - 落点在 `report_finding` / `record_fact` 的字段语义与 `finding_recorder.go` 的校验。
  - 排除结论写回探索图后，planner 态势里的「终态分布 / 方向产出率」才有可信的「排除」口径。
  - 报告「覆盖与排除」章节（0.1.21 已有）直接消费三态数据，声明更有依据。
  - 初期按平台惯例走 settings 开关、先观察模式。

#### M-05 派单计划编译器

- **定位**：把派单纪律从提示词约定变成服务端确定性校验。对标 PentestGPT 计划编译器
  （同行对比 P1 #6）。
- **核心功能需求**
  - 目标必须在授权范围内（已有 N2 守卫在执行侧拦，本模块在派单侧提前拦）。
  - 利用 / 验证类意图必须引用同资产上已完成的观测 fact。
  - 依赖环检测；收尾判定必须引用已完成意图的观测。
  - 每项校验独立开关，初期只开两条。
- **与现有平台的适配逻辑**
  - 落点在 `add_intent` 的服务端处理，与 planner 提示词的「硬底线」互为兜底。
  - 复用 `server/scope_guard.go` 的范围判定函数，不写第二套范围逻辑。
  - 校验失败走与 `steer_work` 相同的回灌机制，把原因喂回 planner，而不是静默丢弃。
  - 串行前置闸门（`requires_intents`）是它的一个特例，合并进同一入口。

### 第二梯队：从一次性测试到持续运营

#### M-06 调度中心（周期任务）

- **定位**：让「重复执行的测试动作」可以按日 / 周 / 月自动触发，是 M-07 和持续型
  攻击面管理的调度底座。对标 fuxi 周期调度。
- **核心功能需求**
  - 调度计划：周期表达式、绑定的任务模板、启停、下次执行时间、执行历史。
  - 触发时按模板创建新任务（不复活旧任务），带独立的授权范围与超时。
  - 同一计划上一轮未结束时不叠加执行。
  - 服务重启后计划不丢。
- **与现有平台的适配逻辑**
  - **边界（重要）**：已有决策是「复测纯手动，禁止自动复测 / 提醒」。本模块只调度
    「新建侦察 / 攻击面类任务」，不调度 `finding_retests`。
  - 创建路径直接走 `launchTask` → `admitTask`，天然获得并发上限与排队，不绕过准入。
  - 模板用已有的 `task_templates`；调度计划是一张新表。
  - 执行历史与结果推送用 `notify` 现有渠道和摘要机制。
  - 注意区分：现有 `scheduler_state` 表是引擎收尾状态，与定时调度无关，不要复用。

#### M-07 资产快照与变更检测

- **定位**：把资产图从「当前状态」变成「有时间维度」，回答「这次比上次多了什么」。
  对标 CVEngine 变更检测。
- **核心功能需求**
  - 按企业 / 范围对资产图做周期快照。
  - 快照 diff：新增 / 消失 / 指纹或标题变化 / 新开放端口。
  - 变更可一键生成「只测新增资产」的任务。
  - 新资产自动过漏洞情报快通道匹配（新爆出的 CVE × 新出现的指纹）。
- **与现有平台的适配逻辑**
  - 资产图是全局共享的，快照天然可以跨任务复用，不绑定任务。
  - 探测复用 `enrich`（DNS 解析 + HTTP 探测的异步 worker 池），不另写探测。
  - 新增资产仍经 `insert_assets` 的范围闸门入库。
  - 变更告警走 `notify` 的过滤规则与摘要周期；任务侧走 M-06 触发。
  - 「未测资产按簇排序」已有，diff 出的新增资产可直接挂进未测清单。

#### M-08 测绘数据源扩展与归一

- **定位**：外部攻击面发现的数据入口。现在是 FOFA（MCP）和 ScopeSentry（同步页），
  各自接入、各自落库。对标 scopesentry / 资产测绘类平台。
- **核心功能需求**
  - 新增 Hunter、Quake、Shodan、ZoomEye 数据源；证书透明度、ASN / Whois 作为补充源。
  - 统一的数据源抽象：凭据配置、查询语法适配、限速、增量游标。
  - 结果归一成平台资产模型（根域名 / 子域 / IP / 服务 / 指纹）后入库，多源去重。
  - 每条资产带来源，可追溯。
- **与现有平台的适配逻辑**
  - 把现有 ScopeSentry 同步（`server/sync_scopesentry.go` + 同步页）和 FOFA MCP
    收敛到同一个数据源接口下，新增源按同一接口实现。
  - 凭据按平台惯例只进运行时配置，回显走掩码（通知渠道的掩码前缀机制可复用）。
  - 入库仍过范围守卫；指纹进 `assets.technologies` 后自动参与漏洞情报联动。
  - FOFA 走的是 MCP，查询结果目前是工具输出文本；本模块应让 FOFA 也走结构化入库。

#### M-09 合规基线核查

- **定位**：在「找漏洞」之外补「合不合规」。面向国内甲方交付中等保、CIS 一类
  基线核查需求。
- **核心功能需求**
  - 内置基线项库：控制项编号、描述、检查方法、期望结果。
  - 核查执行：能脚本化的检查项自动执行，其余生成人工核查清单。
  - 结果分级：符合 / 不符合 / 不适用，附证据。
  - 输出合规核查报告章节。
- **与现有平台的适配逻辑**
  - 基线项是「方法论 + 可执行检查」的组合，符合平台「原生 Go 工具 + 标准化技能包 +
    配套脚本」的新增能力惯例。
  - 不符合项作为一种 vulnclass 类别进 `findings`（枚举表已有别名归一机制），自动获得
    证据、复测、报告、推送全套链路。
  - 自动检查项的命令照常过拦截与审批；只读检查不应被 10 条硬禁误拦，需核对规则。
  - 新增内置技能时遵守「三件事」：frontmatter、默认可见性绑定、发布包含它。

### 第三梯队：交付与开放

#### M-10 报告模板系统与多格式导出

- **定位**：从「单一内置中文模板 + Word / Markdown」升级为可管理的模板与多格式交付。
  对标 Sysreptor。
- **核心功能需求**
  - 模板管理：封面 / 页眉页脚 / 企业标识 / 章节开关 / 术语表可配置。
  - 多格式：PDF（甲方归档常用）、Excel 漏洞清单（甲方资产台账导入常用）、
    在线 HTML 报告（带时效的分享链接）。
  - 同一份数据在页面预览与各格式导出保持同源（A17 已确立的原则）。
- **与现有平台的适配逻辑**
  - **约束**：报告是手写 OOXML、零第三方文档库，这一原则不破。模板是数据不是渲染引擎。
  - PDF 不引第三方库：`docpreview` 已依赖 LibreOffice 做文档转 PDF，Docker 镜像内已有，
    可用同一工具链把 Word 报告转 PDF。
  - Excel 清单是纯数据导出，手写最小 OOXML 即可。
  - 在线 HTML 报告需共享链接 → 依赖 M-12 的访问凭证设计（单管理员会话之外的第二种
    受控访问方式）。

#### M-11 finding 字段 schema 化

- **定位**：让漏洞条目的字段可定义、可校验，报告模板和合规报告才能按字段绑定渲染。
  对标 Sysreptor 字段体系。是 M-10 的前置。

- **核心功能需求**
  - 字段定义：类型、枚举来源（vulnclass / CWE / ATT&CK 已有标签体系）、必填、默认值。
  - 内置 / 预置 / 自定义三级。
  - CVSS 向量自动算分。
  - 按 schema 校验 `report_finding` 入参，错配给人话提示。
- **与现有平台的适配逻辑**
  - 已有基础：vulnclass 19 类枚举与别名归一、技能标签（cwe / attack / class）、
    `report_finding` 的参数容错归一（0.1.21）。本模块把它们收进统一的字段定义。
  - 不另建一套校验分支，扩展现有的归一入口。
  - Word 渲染层按字段 id 绑定，与 M-10 共用。

#### M-12 开放 API 与 API Key

- **定位**：让平台能被 CI、工单、SOAR、客户自己的系统调用。现在只能人登录用。
- **核心功能需求**
  - API Key 的创建、命名、权限范围、过期、吊销。
  - 对外接口子集：创建任务、查任务状态、拉发现、触发报告导出、订阅事件。
  - 通用 Webhook 已是通知渠道之一，需明确事件类型与签名校验规范。
  - 审计：每个 Key 的调用记录。
- **与现有平台的适配逻辑**
  - 现有认证是 `requireAuth`（server/auth.go，jti + 吊销哨兵），单管理员。
    API Key 是**同一账号下的程序化凭证**，不是多用户——不与「不做多用户」的决策冲突。
  - Key 认证做成 `requireAuth` 之外的并列入口，共用下游的业务逻辑与拦截 / 审批
    （开放 API 创建的任务与手动创建的任务受完全相同的管控）。
  - 凭据回显复用掩码前缀机制；限流复用登录侧的全局锁思路。
  - 通知的事件机制（`notification_events`）可直接作为 Webhook 事件源。

#### M-13 MCP 服务端出口

- **定位**：平台现在只能作为 MCP **客户端**调用外部工具；反过来，把平台能力
  （流量检索、漏洞情报、资产查询、建任务）暴露为 MCP 服务端，让 Claude Code / Codex
  这类外部 Agent 能用。对标 M25。
- **核心功能需求**
  - 只读工具优先：流量检索、情报查询、资产查询、发现查询。
  - 写操作（建任务 / 重跑）需显式授权，且必须过拦截与审批。
  - 传输层支持 Streamable HTTP；鉴权依赖 M-12。
- **与现有平台的适配逻辑**
  - `mcphttp` 目前只有客户端，服务端是新增；stdio 由 norma 的 mcp 包负责，不用动。
  - 每个暴露的工具在服务端仍然走 `guard` 的 PreToolUse 链路——外部 Agent 不能绕过管控。
  - 工具可见性的现有机制（30 个上限 + 延迟加载）可用来控制暴露面。

### 第四梯队：Agent 运营基础设施

#### M-14 回归评测靶场

- **定位**：评测基线（0.1.21）只能聚合真实任务；没有标准答案，改了提示词 / 换了模型
  不知道是变好还是变坏。需要一个可重复的靶场和机器判卷。对标 CAIBench 式回归评测。
- **核心功能需求**
  - 一组本地靶场（带已知漏洞清单）。
  - 机器判卷：按响应特征断言漏洞是否被找到、证据是否成立。
  - 五指标：token / 轮数 / 发现数 / 误报数 / 墙钟。
  - 每版跑一次，与上一版对比，防回归。
- **与现有平台的适配逻辑**
  - 直接扩展 `db/eval.go` / `server/eval.go`：评测基线已支持「固定任务集」，把靶场任务
    登记为固定任务集即可复用聚合逻辑。
  - 靶场用 Docker Compose 起在本机，目标在授权范围内，scope 守卫放行。
  - 判卷结果与「单位发现成本」同一套指标口径。
  - 这是同行对比里明确的「阶段 C 先行」——它是其他 Agent 侧改动（M-04、M-05）
    的验收工具，实际排期可以提前到第一梯队之后立即做。

#### M-15 模型价格表与成本核算

- **定位**：已有 token 计量与单位发现 token 成本，缺「折合多少钱」。此前因平台没有
  价格表而未做，硬造报价会失真。
- **核心功能需求**
  - 每个模型通道可填输入 / 输出 / 缓存单价（可留空）。
  - 成本按任务 / 意图 / 角色聚合；价格未填的通道标「未知」而不是按 0 算。
  - 可选：任务级金额上限，达上限收敛、超限收尾。
- **与现有平台的适配逻辑**
  - 数据源是已有的 `llm_usage`，只加价格维度，不改计量。
  - 价格挂在 `llm_profiles` 上（通道自带定价），不另建全局价格表。
  - 任务级金额上限复用任务级预算网关（`server/task_budget.go`）的阈值收敛 / 上限收尾
    两档机制，加一种计量单位。
  - 洞察页「单位发现成本」加一列金额。

#### M-16 隔离执行沙箱

- **定位**：工具现在直接跑在部署主机上。提供任务级隔离执行环境，并作为 PoC 的
  预验证环境（PoC 在沙箱里对仿制目标跑通才标已验证）。对标 M13。
- **核心功能需求**
  - 按任务创建隔离的执行容器，工具链可用，出口仍走平台代理（流量留痕不绕过）。
  - 任务结束自动回收。
  - PoC 预验证：从目标指纹生成仿制环境，PoC 先打仿制环境。
- **与现有平台的适配逻辑**
  - **约束**：同行对比里明确「不抄重型容器编排栈」。本模块是单机容器隔离，不是多机编排。
  - 流量必须继续过 MITM：容器的出站走平台出口代理，否则证据链断裂——这是本模块
    成败的关键约束。
  - 特权动作仍经 hostd；hostd 的拒绝降级机制要覆盖容器内发起的请求。
  - 改动面大，PoC 预验证部分建议先做可行性验证再立项。

## 9. 所有模块共同遵守的现有约束

摘自 `AGENTS.md`，任何新模块都适用：

- 新工具必须注册进三张工具清单和 `agent/toolcatalog.go`；纯读工具用 `readTool` / `readExpTool`。
- 拦截规则新增走 seed 批次，并配按名补种 + enabled 工具集合并。
- 数据迁移走 `schema.sql` 幂等迁移，不改用户持久化数据。
- 结构性改动默认关、settings 可回退，先观察模式。
- 凭据只进运行时配置，回显掩码，不入仓库、不入报告、不写进对话。
- 不可信工具输出加边界标签；URL / 请求头参数严格校验。
- 测试连真 PG、`-p 1`；不写短 sleep 断言。
