# 设计稿：代码资产与 SAST/SCA 联动（M-02）

> 状态：设计稿，未实现。本文档回答「为什么要做、做成什么样、怎么接进现有机制」，
> 不含实现代码。立项前请先看 §8 的待确认项。

## 1. 为什么做

平台目前是「黑盒为主」：从域名/IP 出发，靠 HTTP 与宿主工具探测。三条明确的价值缺口：

1. **白盒结果进不了图谱**。`semgrep` / `gitleaks` / `trivy` 已在宿主工具清单里
   （`hosttools/hosttools.go` 的 `CatCode` 组），但它们的输出只是 Bash 回显——
   worker 看过就丢，规划者看不到「这个仓库有 37 处 sink」，也做不了覆盖统计。
2. **SAST 与动态挖掘之间没有桥**。动态侧发现了「`/api/order` 接受 `id` 参数」，
   但不知道后端是哪段代码、用了什么 ORM、有没有参数化——这正是白盒能直接回答的。
3. **成分分析无法落到情报库**。`trivy` 能列出组件与版本，但结果没进
   `vuln_cpe_products` 的匹配链路，也就无法回答「这个组件版本命中了哪些 CVE」。

一句话：**源码是与域名/IP 同等重要的一类资产，现在它还不是资产。**

## 2. 边界（明确不做）

- **不做通用代码扫描平台**。不自建规则引擎、不做增量 diff 扫描编排（P2 再说）、
  不做代码托管平台对接（GitLab/GitHub OAuth）。
- **不执行样本代码**。静态分析只读文件，不跑构建、不跑测试、不 import 目标代码。
- **不改 `assets.type` 的 CHECK 约束**。现有 6 类型（root_domain/ip/subdomain/app/
  service/endpoint）是全平台共享的枚举，动它要改资产去重、覆盖统计、前端分组。
  代码资产用**独立表 + 锚点**挂进图谱（§3.2）。

## 3. 数据模型

### 3.1 新表

```sql
-- 代码资产：一个仓库 / 一个源码包。归属企业，参与授权范围判定。
CREATE TABLE IF NOT EXISTS code_assets (
    id           BIGSERIAL PRIMARY KEY,
    company_id   BIGINT REFERENCES companies(id) ON DELETE SET NULL,
    task_id      BIGINT,                    -- 首次登记的任务（0=全局）
    name         TEXT NOT NULL,             -- 仓库名或包名
    kind         TEXT NOT NULL DEFAULT 'repo',  -- repo | archive
    location     TEXT NOT NULL DEFAULT '',  -- git URL 或本地路径（archive 时为存储路径）
    default_branch TEXT NOT NULL DEFAULT '',
    language     TEXT NOT NULL DEFAULT '',  -- 主语言（可从文件扩展名推断）
    file_count   INT NOT NULL DEFAULT 0,
    loc          INT NOT NULL DEFAULT 0,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (company_id, name, kind)
);

-- 静态扫描结果：SAST（semgrep）/ 密钥（gitleaks）/ 成分（trivy）
CREATE TABLE IF NOT EXISTS code_scan_results (
    id          BIGSERIAL PRIMARY KEY,
    code_asset_id BIGINT NOT NULL REFERENCES code_assets(id) ON DELETE CASCADE,
    scanner     TEXT NOT NULL,        -- semgrep | gitleaks | trivy
    rule_id     TEXT NOT NULL DEFAULT '',
    severity    TEXT NOT NULL DEFAULT '',
    file_path   TEXT NOT NULL DEFAULT '',
    line_start  INT,
    line_end    INT,
    snippet     TEXT NOT NULL DEFAULT '',
    -- 成分分析专用：组件 + 版本 + 生态（用于 CPE 匹配）
    package_name    TEXT NOT NULL DEFAULT '',
    package_version TEXT NOT NULL DEFAULT '',
    package_ecosystem TEXT NOT NULL DEFAULT '',
    -- 去重与增量：同一仓库同扫描器同规则同位置的重复扫描不堆行
    fingerprint TEXT NOT NULL DEFAULT '',
    scanned_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (code_asset_id, fingerprint)
);
CREATE INDEX IF NOT EXISTS idx_code_scan_asset ON code_scan_results(code_asset_id, scanner);
CREATE INDEX IF NOT EXISTS idx_code_scan_pkg ON code_scan_results(package_name, package_version)
    WHERE package_name <> '';
```

### 3.2 与双图的挂接

**资产图**：`code_assets` 不并入 `assets` 表，而是通过 **锚点** 挂到双图：

- 探索图节点（fact/intent/finding）的 `asset_ids` 不装代码资产 id（id 空间不同）；
- 新增 `code_asset_anchors(code_asset_id, exploration_id, node_id)` 边表，或在
  `exploration_anchors` 上增加 `kind='code_asset'` 的一类锚点（推荐后者：复用现有
  锚点表，不新增一张表）。

> 需要先确认：`exploration_anchors` 是否有 `kind`/`target_kind` 列，以及
> `AddNode` 的锚点校验是否会拒绝非 `assets.id` 的值。**这是本设计的第一待确认项。**

**授权范围**：代码资产的归属走 `company_id`，范围判定复用
`AssetStore.ClassifyAssetsForTask` 的「own/source/foreign」思路——但代码资产不是
资产行，需要在 `db/task_scope_guard.go` 旁新增一个 `ClassifyCodeAssetsForTask`，
按「任务 scope 是否覆盖该企业」判定。写回守卫（`scopeGuardError`）增加代码资产分支。

## 4. 工具设计

按平台惯例「只落脚本 + 组命令，不自己发请求」（`agent/tools_probe.go`）：

| 工具 | 类型 | 作用 |
|---|---|---|
| `code_asset_register` | 写 | 登记仓库/源码包（git URL 或已上传的 archive），返回 code_asset_id |
| `code_scan_plan` | 读 | 生成扫描命令（semgrep / gitleaks / trivy），只给命令不给结论 |
| `code_scan_ingest` | 写 | 把扫描器 JSON 输出结构化入库，返回「入库条数 / 命中分布 / 新增高价值项」 |
| `code_asset_context` | 读 | 按运行时资产（域名/URL）反查关联代码资产与相关 sink 位置 |

设计要点：

- `code_scan_plan` 与 `fuzz_plan`（M-01）同一模式：输出 `run_with_bash`，流量与审批
  照常；扫描是本地读文件，不产生网络流量，但仍需过拦截（防止顺手 `git clone` 到
  未授权仓库）。
- `code_scan_ingest` 接受扫描器的 JSON 文件路径（worker 先跑命令把结果写到工作目录），
  解析后入库。**不接受模型手写的结果**——与「工具输出是判据」的既有取向一致。
- 入库后把「高危规则命中」写成探索图 `fact`（带 code_asset 锚点），让 planner 的
  态势里能看到「这个仓库有 N 处可控输入进 sink」，从而派动态验证意图。

## 5. 与现有模块的适配

### 5.1 漏洞情报（`vulnintel`）

`trivy` 的成分结果（package + version + ecosystem）写入 `code_scan_results` 后，
复用 `vulnintel` 的 CPE 匹配：

- 现状：`vuln_cpe_products` 按 vendor/product + 版本区间匹配；
- 桥接：`code_scan_ingest` 入库后调用一次 `vulnintel` 的匹配函数，命中项写成
  `hint` 节点（「组件 X 1.2.3 命中 CVE-2024-XXXX」），与「资产指纹反查 CVE」同一条路径。

> 待确认：`vulnintel` 的匹配函数是否接受「无 CPE、只有包名+生态」的输入。
> 现有实现基于 CPE 三态判定，npm/pypi 生态名需要一次映射（可比 GHSA 的生态字段）。

### 5.2 技能

`skills/source-code-hunting` 已存在（白盒方法论）。只需补一节「平台工具映射」
（与 `api-security-testing` 本轮补 `fuzz_plan` 的做法一致），不新建技能。

### 5.3 报告

`report` 包已有「客户端/二进制分析」章（`writeReverseChapterDocx`）。代码扫描结果
可以有独立小节或并入该章——**倾向独立小节**，因为二进制与源码的读者关注点不同。
模板开关沿用 M-10 的 `Sections`（新增键 `code_scan`）。

## 6. 分阶段落地

| 阶段 | 内容 | 产出 | 验证方式 |
|---|---|---|---|
| P1 | 登记 + 扫描入库 + hi 高价值项写 fact | 4 个工具、2 张表 | 用本仓库自身跑 semgrep，断言入库条数与分布 |
| P2 | 成分分析 → 情报匹配桥 | CPE/生态映射 | 用已知组件版本断言命中指定 CVE |
| P3（暂缓） | 增量扫描（按 commit diff 只扫变更文件） | — | 需要先有稳定的扫描基线 |

## 7. 迁移与回滚

- 新表 + 幂等 `CREATE TABLE IF NOT EXISTS`，`schema.sql` 尾部追加；
- 不 ALTER `assets`，不动资产去重与覆盖统计——回滚只需 DROP 两张新表；
- 工具全部通过 `BuiltinToolSeeds` 自动入目录，关闭时可按 agent 取消绑定。

## 8. 待确认项（立项前必须回答）

1. `exploration_anchors` 是否支持非资产锚点（§3.2）？如果不支持，是新增边表还是扩展
   `kind` 枚举？这决定 P1 的数据模型。
2. 源码包上传复用逆向样本的分片上传链路，还是新增独立上传端点？逆向样本有 512MB
   上限与 24h 会话清理，源码包可能更大。
3. `vulnintel` 的 CPE 匹配能否接受生态名（npm/pypi/maven）？不能的话 P2 是否值得做？
4. 代码资产的「已测覆盖」怎么算——按文件数还是按 sink 数？影响报告覆盖率口径。

## 9. 风险

- **规模**：一个中型仓库 semgrep 结果可达数万条，全量入库会撑爆 `code_scan_results`。
  P1 需要在 `code_scan_ingest` 里做上限与折叠（如只入 critical/high + 每规则前 N 条）。
- **误报**：SAST 误报率天然高。入库时必须标 `scanner` 与 `rule_id`，报告里不能与
  已确认漏洞并列——应单列「静态扫描线索」，并明确「未经验证」。
- **法律边界**：只允许登记**授权范围内**的代码仓库。`code_asset_register` 必须过
  拦截规则与审批（`git clone` 到非授权仓库属于越界）。
