# 典型脱敏案例

> 所有案例已脱敏，仅用于说明手法与证据口径；实际测试以授权范围为准。

## 案例 1：硬编码 AppSecret → 任意 openid

- 面：源码与密钥（3）+ 开放能力（39）。
- 发现：解包产物 `app.js` 里 `appsecret: "xxxx"`；`miniprogram_audit` 命中。
- 验证：用该 AppSecret 调一次 `jscode2session`，成功换回 openid/session_key。
- 证据：静态命中位置 + 一次换票回执（secret 脱敏）。
- 教训：AppSecret 泄露常与手机号解密接口联动，优先确认影响面。

## 案例 2：详情接口 IDOR

- 面：越权（9）。
- 发现：`GET /api/order/detail?id=1001` 用 A 的 token 返回 B 的订单。
- 验证：A token + A id → A 数据；A token + B id → B 数据。
- 证据：两条对照响应，保留订单号脱敏特征。
- 教训：越权必须双身份对照，单条「能查到」不能证明。

## 案例 3：云函数未授权

- 面：云开发（34）/（35）。
- 发现：`callFunction({name:"getUserInfo"})` 不校验 openid，入参传谁就返回谁。
- 验证：未登录调用 + 传他人 openid，返回其资料。
- 证据：请求体（env/函数名/入参）+ 响应一条（脱敏）。
- 教训：云函数常把 `event.openid` 当可信身份，实际来自客户端。

## 案例 4：云数据库直连读他人数据

- 面：云开发（36）。
- 发现：客户端可直连集合，`where({_openid: 他人})` 返回数据。
- 验证：只读一条，证明权限缺口；不批量导出。
- 证据：查询条件 + 一条记录 + 权限配置推断。
- 教训：集合权限设为「所有用户可读」是常见配置错误。

## 案例 5：支付回调伪造

- 面：业务逻辑（15）/ 开放能力（42）。
- 发现：回调未校验签名/证书，可构造 `TRANSACTION.SUCCESS` 通知。
- 验证：测试订单伪造回调，订单状态变为已支付。
- 证据：回调体 + 订单状态前后对照。
- 教训：金额篡改（14）与回调伪造（15）要分开报，修复点不同。

## 案例 6：sourcemap 还原挖出隐藏接口

- 面：源码（2）/ 接口（6）。
- 发现：包内 `.map` 可还原源码，发现未在小程序页面使用的内部接口。
- 验证：接口无鉴权，直接返回配置/用户列表（少量）。
- 证据：还原源码片段 + 接口回执。
- 教训：先看 sourcemap，再做接口测试，效率最高。
